# HARD-GATE：先问清，后动手

本规则优先于分类、定性、法规引用和报告成文。目标是把“需要审计人员决策的专业判断”和“可由稳定配置自动执行的格式习惯”分开。

## 待决策结论码与事实一一对应（V2.2.3）

三个待决策结论码各自绑定唯一事实，机器结果中必须**分别完整发射**，不得用一个泛化码吞并兄弟码：

- `blank_record`（问题描述空白）→ `decision_required_blank_record`；
- `inclusion_decision_needed`（只有摘要和金额的汇总行等纳入/排除取舍）→ `decision_required_record_inclusion`；
- `pending_or_unconfirmed_facts`（“待落实/是否有文件”等未确认事项）→ `decision_required_pending_items`。

发射前调用 `python3 scripts/classification_emission.py decision-required --input <facts.json>`，按其输出 `codes` 完整发射：有几个事实为真就发几个码，缺一个事实就少一个码。每个码还须通过结论事实 grounding 边界（`rules/result-contract.md`）附各自事实的逐字引文。

## 必须阻断

以下事项未解决前，不得形成正式审计认定：

1. **记录取舍**：汇总参考行、空白问题描述、重复记录是否纳入；
2. **拆分与合并**：同一原始记录是否拆分为多个独立 Finding，或多个同类事项是否合并；
3. **跨类归属**：主分类存在实质冲突，且不同选择会改变整改责任或法规依据；
4. **金额口径**：凭证金额、问题金额、已确认差额、待核实金额之间存在冲突；
5. **重大定性**：从一般管理问题升级为违反财经纪律、涉嫌违法违规等；
6. **法规适用**：地区、单位层级、单位性质、人员身份、业务年度、资金性质等关键条件未知，且会改变法规是否适用；
7. **正式问题/待核实**：证据不足事项是否进入正式问题存在争议；
8. **决策比对结论**：账面付款与会议纪要比对得出“未见议定事项”结论后、被查单位核对确认前（见下节）。

阻断时输出《待决策事项清单》：原始记录 → 已知事实 → A/B/C 选项 → 推荐项及理由 → 不决策的影响。用户未答复的事项保持“待核实”，不得先写正式结论再事后解释。

## 决策比对“未见事项”的被查单位核对确认

以会议纪要为基准比对账面付款得出的“未见对应议定事项”，只是**比对结论，不是违规事实**——纪要通常只覆盖集团层面决策，子公司内部会议记录、付款审批单、授权文件同样可以是有效决策依据。该类事项进入正式问题前，必须完成被查单位核对确认程序：

1. 向被查单位书面提交“未见”清单，要求其限期提供内部决策记录（内部会议纪要、付款审批单、授权文件）或书面说明；
2. 被查单位补充了有效决策记录的，转为已议定/有授权事项，从正式问题中移除；
3. 被查单位不能提供且无书面说明的，方可写入正式问题，事实段必须写明“经被查单位核对确认，未能提供集团或其他层面的决策记录”，并保留口径说明：“未见纪要议定记录不等于未召开内部决策会议”；
4. 未执行核对程序且不具备执行条件（如被查单位已注销、离任审计、突击举报核查）的，事项整体保持“待核实”状态，报告中写明未执行核对的原因。

未完成核对确认的“未见”事项，不得计入正式问题的金额合计；报告如需披露，只能列入待核实事项清单并单独统计。

## 不再反复询问

以下稳定习惯从 `profiles/firm-default.yaml` 读取，已经配置后不再重复询问：

- 日期格式；
- 金额格式；
- 中文引号；
- 凭证引用格式；
- 普通费用标题归并习惯；
- 报告模式名称及既定事务所格式。

首次合作或用户明确提供新模板时，可以更新 profile；不得把专业判断塞入 profile 规避 HARD-GATE。

## 纯事实事项

能从原始材料、凭证附件或可靠公开资料直接查明的事实，不应让用户代替检索。查明后记录来源；仍无法查明且影响判断时，才进入 HARD-GATE。
